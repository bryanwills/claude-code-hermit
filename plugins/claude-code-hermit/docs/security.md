# Security

Safety model for autonomous hermit agents — deny patterns, defense in depth, and operational recommendations.

---

> **Important:** Deny patterns are blocklist-based string matches. They block known dangerous commands but cannot prevent all harmful invocations. The default `auto` mode reduces (but does not eliminate) the need for container isolation by requiring classifier review of each action. Auto mode is generally available to all users across subscription plans and API usage; current Claude Code version, model, provider, and administrator settings can still affect availability. If it is unavailable for the current selection, choose a supported model or another permission mode. Always use container isolation when running with `bypassPermissions`. See [Known Limitations](#known-limitations) below.

## Deny Patterns

Block tool invocations regardless of permission mode. Generated by `/claude-code-hermit:hatch` (step 9) or `/claude-code-hermit:docker-setup`. Canonical source: `state-templates/deny-patterns.json`.

### Default set (all deployments)

```json
{
  "permissions": {
    "deny": [
      "Bash(rm -rf *)",
      "Bash(rm -fr *)",
      "Bash(rm -r -f *)",
      "Bash(rm -f -r *)",
      "Bash(*/rm -rf *)",
      "Bash(*/rm -fr *)",
      "Bash(*/rm -r -f *)",
      "Bash(*/rm -f -r *)",
      "Bash(chmod 777*)",
      "Bash(*sudo *)",
      "Bash(*> /etc/*)",
      "Bash(curl * | bash*)",
      "Bash(wget * | bash*)",
      "Bash(env)",
      "Bash(printenv)",
      "Bash(cat .env*)",
      "Bash(cat */.env*)",
      "Bash(cat ~/.ssh/*)",
      "Bash(cat ~/.aws/*)",
      "Bash(*API_KEY*)",
      "Bash(*SECRET*)",
      "Bash(*TOKEN*)",
      "Bash(*> *.claude-code-hermit/OPERATOR.md*)",
      "Bash(*>.claude-code-hermit/OPERATOR.md*)",
      "Edit(*/.claude/plugins/marketplaces/*)",
      "Write(*/.claude/plugins/marketplaces/*)"
    ]
  }
}
```

The `rm` entries cover four flag orders (`-rf`, `-fr`, `-r -f`, `-f -r`) in both bare and path-prefixed (`/bin/rm`, `./rm`) spellings — see [Known Limitations](#known-limitations) for exactly what this does and does not catch.

### Always-on additions (Docker / tmux)

```json
{
  "permissions": {
    "deny": [
      "Bash(ssh *)",
      "Bash(docker *)",
      "Bash(kubectl *)",
      "Bash(npm publish*)",
      "Bash(git push --force*)",
      "Bash(git push origin main*)",
      "Bash(git reset --hard*)",
      "Bash(*--no-verify*)",
      "Edit(*.claude-code-hermit/OPERATOR.md)",
      "Write(*.claude-code-hermit/OPERATOR.md)",
      "Edit(*.claude-code-hermit/config.json)",
      "Write(*.claude-code-hermit/config.json)",
      "Edit(*.claude/settings.json)",
      "Write(*.claude/settings.json)",
      "Edit(*.claude/settings.local.json)",
      "Write(*.claude/settings.local.json)",
      "Edit(*.claude/output-styles/hermit-voice.md)",
      "Write(*.claude/output-styles/hermit-voice.md)",
      "Bash(*> *.claude/settings.json*)",
      "Bash(*> *.claude/settings.local.json*)",
      "Bash(*> *.claude/output-styles/hermit-voice.md*)",
      "Bash(*> *.claude-code-hermit/config.json*)",
      "Bash(*>.claude/settings.json*)",
      "Bash(*>.claude/settings.local.json*)",
      "Bash(*>.claude/output-styles/hermit-voice.md*)",
      "Bash(*>.claude-code-hermit/config.json*)"
    ]
  }
}
```

Only the five `git`/`npm`/`--no-verify` entries reach the native `settings.json permissions.deny` array (via `apply-settings.ts deny hardened`) — `ssh`/`docker`/`kubectl` are valid in devops contexts on the host and deliberately excluded even from hardened mode, and the OPERATOR.md/`settings.json`/`settings.local.json`/voice-file/`config.json` guards are enforced by the runtime hook (`AGENT_HOOK_PROFILE=strict`) only, since they protect files the hook itself reads at startup.

**The `config.json` guard is a policy guard, not a filesystem boundary.** It keeps an unattended session's *tool* writes — `Edit`, `Write`, and `>` redirects — on the `settings-edit`/`hatch-config`/`evolve-finalize` paths, which validate the whole config and record every change in the settings ledger. It does not stop `cp`, `tee`, `sed -i`, a redirect written against an absolute path with no space (`echo x>/abs/…/config.json`), or a script writing through `fs` — the same depth as the OPERATOR.md and settings guards above. Both the `Edit(…)` and `Write(…)` spellings are required here even though the native permission engine folds Write into an Edit glob — this hook matches tool names exactly.

**A glob carrying `>` is matched per compound segment, not against the whole command.** A redirect and its target always sit in the same segment, so scoping it there keeps the guard while dropping the collateral: `bun x.ts 2> /dev/null; cat .claude-code-hermit/config.json` is a pure read, and `echo done > /tmp/log; bun …/settings-edit.ts .claude-code-hermit/config.json set …` is the sanctioned writer these patterns exist to funnel writes onto — matching the whole command would block both by pairing an unrelated redirect with a later mention of the path. Every other glob still sees the whole command, which `Bash(curl * | bash*)` needs. Remaining limit: the glob is not quote-aware, so a quoted `>` in the *same* segment still matches (`jq ".spend > 5" .claude-code-hermit/config.json` is blocked).

**Every path glob here needs its leading `*`.** Hooks receive an absolute `file_path` and the matcher anchors the pattern at both ends, so a bare `Edit(.claude/settings.json)` matches nothing a real tool call ever sends. The settings entries shipped without it and were inert until fixed; the same shape now covers `.claude/output-styles/hermit-voice.md`, which is guarded for the same reason OPERATOR.md is — it is loaded into the next session's system prompt, so an unattended session must not be able to rewrite how it talks.

`/claude-code-hermit:docker-setup` applies both sets (default + always-on). `/claude-code-hermit:hatch` hardened mode applies both sets minus `docker/kubectl/ssh` (valid on host). Hatch minimal mode applies the default set only.

## Defense in Depth

| Layer               | Where           | Enforcement           |
| ------------------- | --------------- | --------------------- |
| Deny patterns       | `settings.json` | Mechanical*           |
| Bash sandbox        | `settings.json` (`sandbox.*`) | Kernel-enforced (`bwrap`); Claude Code's own native sandbox — hermit does not configure it, see [Bash Sandbox](#bash-sandbox) below |
| Agent-level rules   | `agents/*.md`   | Instruction-following |
| Hook enforcement    | `hooks.json`    | Mechanical            |
| Config isolation    | Named volume    | Mechanical            |
| Container isolation | Docker/VM       | Mechanical            |
| Container hardening | docker-compose.hermit.yml | Kernel-enforced (defense in depth — `no-new-privileges` is load-bearing; cap drops + PID cap are incremental) |
| Advanced hardening (opt-in) | docker-compose.security.yml | Kernel-enforced (LAN block + DNS policy, resource bounds, sysctls — opt-in via `/docker-security`; LAN containment is the load-bearing layer here) |
| OPERATOR.md         | OPERATOR.md     | Instruction-following |

*\* **Deny rule caveat:** There are reported bugs where `Edit`/`Write` deny rules in `settings.json` are not always enforced — Claude Code has been observed editing files that match a deny pattern. Deny rules are the correct approach and best available option, but can't be treated as airtight today. For OPERATOR.md specifically, Claude Code's built-in `.claude/` directory protection adds a second layer. Combined, OPERATOR.md modification is unlikely but not impossible until Anthropic fixes deny rule enforcement.*

## Unattended Asks

A channel-primary hermit (`always_on: true`, at least one reachable channel) has no attached interactive surface: nobody is watching the tmux pane. Anything that calls a synchronous ask primitive there — `AskUserQuestion`, a native permission prompt, a harness-rendered dialog — stalls the session invisibly: the pane blocks waiting for a keypress, and from the channel the hermit just goes quiet. The taxonomy for handling this, in order of preference:

1. **Pre-authorize** — grant the permission ahead of time (`permission_mode`, deny patterns) so the prompt never fires.
2. **Out-of-process** — resolve the decision outside the blocked turn entirely (the pause/resume keyword flow).
3. **Async approval** — bridge the question to the channel and let the answer arrive as a later message, so the turn can move on. This is the model for both binding instances below.
4. **Fail-loud** — when a prompt can't be redirected, notify the operator that something is stuck rather than silently hanging.
5. **Native bridge** — defer to a first-party mirror/answer path once Anthropic ships one, and shrink custom machinery accordingly.

Never bypass — no auto-answering a permission prompt, no sending Escape on the operator's behalf. Deciding what an unattended agent is allowed to do is always the operator's call, made in advance (config) or asynchronously (channel reply), never invented by the hermit in the moment. The narrow exception is Claude Code's cached-context warning immediately after a trusted sender requested an exact `/model <arg>` or `/effort <arg>`: that sender already made the switch decision, so the Stop hook confirms only the command-specific, freshly-correlated dialog. Every other native dialog remains untouched.

A permission-mode switch requested from a channel (`/permission-mode <mode>`) is governed by that same clause, and is not covered by the dialog exception above — Shift+Tab is a keybinding, not an answer to a prompt, so nothing here is being auto-confirmed on the operator's behalf. What makes it safe is the direction of travel and the guards around it: only `default`, `acceptEdits`, and `auto` can be reached from a channel, so a chat message can tighten what the session may do unattended but never widen it past what boot already allowed. `bypassPermissions` is refused outright — its terminal acknowledgement (`hermit-start.ts`) exists precisely so that a present operator authorizes it. `plan` is refused for a different reason: it would leave the hermit unable to answer the channel it was asked from, and unable to be switched back. The cycler reads the mode off the status bar before every keystroke and stops the moment it cannot, which is also what keeps it from pressing anything while a dialog is open — the status bar is not on screen then. The switch lasts only for the session; a restart re-asserts `config.permission_mode`, so the durable answer to "what may this hermit do" stays in config where the operator set it.

Two binding instances exist today:

- **Hermit-owned skills (async approval, cooperative):** every core skill either carries the Step-0 channel-reply marker and routes its asks through the micro-proposal bridge, or contains no interactive ask at all — enforced by a static contract test (`tests/channel-ask-contract.test.ts`) that fails CI the moment a skill adds an unbridged ask.
- **Everything else (async approval + fail-loud, deterministic):** built-in flows, other installed plugins' skills, and spontaneous model-initiated questions are invisible to that static scan. A PreToolUse hook (`scripts/ask-gate.ts`, matcher `AskUserQuestion`) denies the call on a channel-primary session with a redirect reason that steers the model to the channel reply tool plus a durable `micro-proposals.json` entry — deny-steering behavior is probe-verified, the model does not retry the tool. The gate fires only on the **managed unattended session**, identified by the `HERMIT_MANAGED` marker `hermit-start` stamps into that session's tmux env-file (never `settings.local.json` or the docker-compose env block). This scopes the deny per-session rather than by the project-wide `always_on` config: a hand-launched maintenance `claude` in the same project — or a `docker exec` shell — lacks the marker, so its interactive AskUserQuestion flows (`/hermit-evolve`, `/hermit-settings`, `/docker-setup`) are never denied out from under a present operator. The gate leans **allow** on any ambiguity, because a false-allow is caught by the watchdog's fail-loud check below while a false-deny would silently break the operator's flow. Prompts that can't be redirected this way (native permission dialogs, harness-rendered prompts below the tool layer) are instead caught by the watchdog, which recognizes a stalled dialog on the captured pane, pushes one deduped operator notification per episode, and — critically — suppresses its own wedge nudges and re-arm keystrokes for that pane so it never auto-answers the pending prompt. A channel whose recent sends are failing (revoked token, etc.) is not treated as a valid redirect target either — tracked via advisory `state/channel-health.json` (written by `lib/channel-send`) — so the ask falls through to the native prompt and the watchdog backstop above instead of being denied into a channel that can't deliver. Opt out globally with `ask_gate: false`, or per-session by launching with `HERMIT_ASK_GATE=off`; the watchdog check is unconditional on any `watchdog.enabled` hermit.

**Revisit trigger:** if Anthropic ships a mirror or native permission-request bridge that lets the Claude app notify or answer a pending dialog on a headless session, both the gate's scope and the watchdog's pattern check should shrink accordingly — check current mirroring behavior before assuming this custom machinery is still the whole story.

## Auto-mode Classifier

Claude Code's `--permission-mode auto` (the hermit's default) routes tool calls through a classifier that blocks anything it judges irreversible, destructive, or aimed outside the trusted environment — a second gate that runs after the permissions system, before a tool call executes. The live tmux probes used for the implementation ran on CC 2.1.201 with `--model sonnet`; current model/provider availability is governed by Claude Code rather than hard-coded here. Those probes settled how a hermit's own sealed settings writes interact with the classifier:

- **Tiers and resolution.** `autoMode.hard_deny` blocks unconditionally — the only way past it is an out-of-session executor (see below). `autoMode.soft_deny` (which includes the classifier's built-in `[Self-Modification]` rule — an agent widening its own `permissions.allow`) is cleared by either explicit intent in the operator's own live message, or a seeded `autoMode.allow` exception. The `ask_gate` tier above is a different mechanism entirely (a hermit-owned `PreToolUse` hook), not the classifier.
- **`autoMode` config is read only from `~/.claude/settings.json`, managed settings, or `--settings`** — never from a project settings file. Claude Code 2.1.207 dropped `.claude/settings.local.json` from that list (a repo or build step could otherwise inject its own classifier rules); committed project settings were never read. Re-probed on 2.1.239 with a sentinel rule and `claude auto-mode config`: user scope and `--settings` show it, both project files do not. The misplacement is silent and the settings JSON Schema doesn't mark the key user-only — upstream [anthropics/claude-code#87545](https://github.com/anthropics/claude-code/issues/87545). A hermit therefore ships its policy **per session**: `hermit-start` renders `.claude-code-hermit/state/claude-settings.overlay.json` (atomic tmp+rename, rebuilt every boot, entries sealed in `lib/settings/automode-entries.ts`) and launches with `--settings <overlay>`. Nothing is written to the operator's user settings: one project's policy must not follow them into every other Claude session, and with no cross-project locking two hermits booting could clobber each other's merge. The predecessor `apply-settings.ts automode-seed` op is retired and exits 1.
- **Auto mode suspends wildcarded-interpreter allow rules.** Every `Bash(bun */scripts/*.ts*)` rule in the hermit's sealed allow-list (`apply-settings.ts` `allow` op) is wildcarded, so under auto mode all of them re-enter the classifier. Three exact resolver grants are the narrow exceptions: `Bash(.claude-code-hermit/bin/hermit-run channel-send *)`, `Bash(.claude-code-hermit/bin/hermit-run observations observe *)`, and `Bash(.claude-code-hermit/bin/hermit-run proposal shell-append *)`. They pre-clear only those ad hoc model calls; every other maintenance script still cannot rely on base permissions to pre-clear its calls before the classifier.
- **The sealed exception.** The overlay carries a declarative `autoMode.allow` entry plus `autoMode.environment` context pre-authorizing the hermit's own `apply-settings.ts` invocations, including when triggered by a plugin upgrade rather than a live operator message. Both ride the same gating as the artifact grant (`publish_authorized`, a page enabled, default backend), since they exist to clear that path's unattended writes. Tone matters here: a probe session flagged an over-argued exception as "planted pre-authorization justification," so the entry states its constraints plainly and argues for none of them. Because an ALLOW exception is mandatory once matched, its constraints are the only thing bounding it, so the entry is written as a checkable shape rather than a description of intent — path, op and command form are the whole test, since the classifier cannot verify what the script writes. Each clause is deliberate: the script path is anchored to a **concrete prefix computed at render time** rather than a `*/scripts/` glob — `automodeAllowEntry` anchors on the plugins directory (`$CLAUDE_CONFIG_DIR/plugins`, plus the boot root itself when a hermit boots from a checkout) and then constrains the tail: it must end in `/scripts/apply-settings.ts` and its install root must be named `claude-code-hermit` or be a single version directory inside one. The anchor spans install *trees*, not one install, because boot and session resolve this plugin from different ones: `bin/hermit-run` scans the marketplace clone while the harness substitutes `${CLAUDE_PLUGIN_ROOT}` in skill text with the versioned cache copy — anchoring on the boot root alone would leave every in-session call outside the grant, and anchoring on a version would deny the mid-session upgrade path the entry exists to clear. Both paths must be written out literally, with no `..` segment and no unexpanded variable; the **exact argument grammar** is spelled out (`bun <script> <settings-file> <op> [op args]`) with shell chaining, redirection, env-var prefixes, added arguments, and indirection through `npx`/`sh -c`/wrapper scripts/Agent or Workflow prompts all voiding it; the ops are **enumerated** from `SEALED_SETTINGS_OPS` — `apply-settings.ts` dispatches from a hardcoded `switch` and only its usage message reads the constant, so a contract test asserts the two stay in step; the target is the session working directory's `.claude/settings.json` or `.claude/settings.local.json`, never one under `$HOME/.claude/`; `channel-env`'s state-directory argument is called out as the one caller-supplied value it writes; `.mcp.json`, hooks, approval gates and `.claude-code-hermit/config.json` are excluded by an **operative** clause (they remain Self-Modification) rather than by deferring to another entry; the grant is **void** if this session authored the script with a file-editing tool, or if it would achieve a settings change the operator declined this session or that was blocked this session when attempted *by some other means* (an anti-laundering carve — scoped that way on purpose, since voiding on any earlier denial would let one stochastic classifier refusal of `permissions-plan` lock `permissions-sync` out of the same `hermit-evolve` run, with no in-session recovery); and an upgrade or migration may *trigger* the run without the script path, op or target file ever being *sourced from* its instruction text.

  **Accepted residual, by design:** a plugin install or upgrade writing a new version directory deliberately does **not** void the grant. Voiding on it would deny exactly the unattended `hermit-evolve` path this entry exists to clear — that flow upgrades the plugin and then applies settings in the same session. The consequence is that anything able to force a plugin upgrade mid-session can replace the script the grant covers; the compensating controls are the install prefix anchor (an arbitrary path is still outside the grant) and the deterministic gates below, which the classifier cannot override. The terminal-only tier does not depend on any of this — enforcement is the `PreToolUse` gate below.
- **Tiered settings authority.** `hermit-settings` is model-invocable, so a channel message can change safe settings through `settings-edit`'s validated, audited path. The rest is tiered by *where the request came from*, because a `<channel>` envelope is an unauthenticated claim of identity:

  | Tier | Who | What |
  |---|---|---|
  | `allowed` | any chat that reaches the hermit | name, language, cadence, `artifacts.publish_authorized`, … |
  | `maintainer` | the configured `maintainer_channel_id`, allowlist-checked | `boot_skill`, `remote`, `escalation`, `docker.*`, `artifacts.backend`, and anything not named below |
  | `nonce` | maintainer chat **and** an echoed confirmation code | `permission_mode`, `env`, `env.*` |
  | `terminal-only` | the operator's own terminal, on every turn | `allowed_users`, `default_chat_id`, `dm_channel_id`, `maintainer_channel_id`, any ancestor write that would replace them, and any direct `config.json` write |

  The maintainer tier exists because the hermit that most needs these decisions is the unattended one, and its operator is reachable on a channel, not at a shell. Its anchor is the platform-supplied chat id (`lib/channel-auth.ts` `isMaintainerController`), not message text — a materially stronger signal than `user="operator"`, which anyone can send. It is strictly above `isTrustedController`: the home chat carries *control* authority (pause/status), the maintainer chat carries *settings* authority. With no `maintainer_channel_id` configured the tier is inert and everything above `allowed` stays terminal-only.

  **The enrollment root is the deliberate hole in it.** Those four keys are what the tier is anchored on, so a maintainer chat that could add an allowed user or re-point itself would convert one compromise into a permanent, self-extending one instead of something an operator with terminal access can revoke. That is the difference between a privilege the operator can take back and one they cannot, and it is why the list is enumerated rather than derived. Unknown and future keys land on `maintainer`, not the terminal: only the unrecoverable part is enumerated.

  **The nonce tier** covers the two execution-adjacent keys (`lib/settings-confirm.ts`): the hermit posts a short code to the maintainer chat and the operator echoes it back in a second message. A code is bound to one target and one chat, single-use, expires in 10 minutes, and is matched only against the harness-written envelope body — never the model's own tool call, so the model cannot satisfy a confirmation it was told to relay. What that buys is narrow and worth stating plainly: a *passive* compromise of the maintainer chat (a leaked export, an over-shared channel, a stale device) can no longer authorize execution; only someone who can also post as an allowed sender can complete the round trip, and the operator sees a code they never asked for. It does not defend against a writer who can forge transcript entries — that defeats the whole gate, nonce included.

  Three layers enforce this, in decreasing order of strength: (1) **deterministic** — `scripts/channel-settings-gate.ts`, a `PreToolUse` hook that resolves the *current turn's* opening prompt from the transcript (same helper chain as `channel-hook.ts`), keeps the parsed envelope, and exit-2 denies anything above the tier that envelope's chat carries; it keys on the turn, not the session, so an operator typing in the managed hermit's own pane is unaffected, and it fails closed on undetermined provenance only for a protected mutation under `HERMIT_MANAGED=1`. A forged `<channel>` tag pasted into a message body cannot shift which chat a turn appears to come from: `parseChannelEnvelope` is start-anchored and reads attributes from the opening tag only. (2) **classifier guidance** — an `autoMode.soft_deny` entry in the overlay, probe-backed (terminal-typed intent clears a soft block; a channel-enveloped request does not) but not a contract. (3) **model steering** — the skill's Step 0 fence and the CLAUDE-APPEND rule. Honest boundary: the gate matches command shapes, so a sufficiently obfuscated same-user shell write can still evade it; the ordinary direct-write paths are closed in the strict profile's deny patterns.
- **A channel reply can never authorize a permission grant.** Two independent gates discount it: the model itself treats a `<channel>`-enveloped privileged instruction as a likely injection attempt before making any tool call, and even past that, the classifier's own soft-deny provenance test rejects anything not sourced from the operator's live message. So a channel-resolved decision may only flip hermit config (e.g. `artifacts.publish_authorized`) — the actual permission write always happens either attended (hatch/evolve, where the operator's presence satisfies the intent test) or from an out-of-session executor: `hermit-start`'s boot-time grant runs as a plain OS process before the Claude session starts, so it is never subject to the classifier at all.

  **Where `permission_mode` sits.** It lives in config but is functionally a permission, so it is the one key that has to be placed against this invariant explicitly. Two different things carry the name. The **durable config key** is channel-reachable only through the maintainer tier *plus* an echoed confirmation code (§ above) — an active second factor, so a chat message alone still never authorizes it, and the write it performs is to hermit config, not to `permissions.allow`. The **session-scoped `/permission-mode <mode>`** channel command is a separate, narrower path (§ Unattended Asks): it reaches only `default`, `acceptEdits` and `auto`, so it can tighten what an unattended session may do but never widen it past what boot already allowed, and `bypassPermissions` is refused outright. Neither path writes a permission grant, and neither is cleared by a channel reply on its own.
- **`PermissionDenied` notifier.** A `PreToolUse` gate can preempt a stall (see `ask_gate` above), but the classifier's own denials happen inside a tool call the hermit didn't anticipate. The `PermissionDenied` hook (`permission-denied-notify.ts`) makes those visible on the managed unattended session — a deduped, bounded channel message naming the blocked tool and its input (Claude Code's `PermissionDenied` payload delivers `tool_name`/`tool_input`, not the classifier's reason text — that stays in the session transcript and the Recently-denied view, so the alert points the operator at *what* was blocked, not the model's phrasing of *why*) — the deterministic counterpart to `CLAUDE-APPEND.md`'s "Auto-mode denial alert" rule. It cannot block or retry the call; auto-retrying a classifier denial would itself be the bypass this section describes. The model-side rule's follow-up alert is not that bypass: CLAUDE-APPEND sanctions a single alert send about the denial — never a retry of the denied call — falling back to the Progress Log and terminal if that send is denied too, and on managed sessions the rule defers to this hook's alert instead of duplicating it. The client-facing copy of that alert is plain and detail-free ("One action could not run because it needed approval. Work that doesn't depend on it can continue. You don't need to fix this."); the tool name and sanitized input are the maintainer-tier leg (below).
- **Tiered disclosure.** On a client-facing install (`operator_profile: "non-technical"`, or any channel with a `maintainer_channel_id`), operator notifications split by audience. The **maintainer chat** receives the technical, operational, and spend content: tool names and sanitized tool input on a denial, USD/cap figures on a budget alert, watchdog lifecycle events, and the reauth sign-in link. The **client chat** receives only plain-language alerts with no tool detail, no figures, and no internal IDs. Where no `maintainer_channel_id` is configured, `non-technical` suppresses the technical leg to `SHELL.md` Findings rather than the client chat (fail-closed on disclosure); a `technical` install keeps today's contract (the detail may land in the primary chat). Maintainer-tier sends carrying credential material (the reauth link) are marked sensitive and skip the searchable channel log. A maintainer chat is **outbound-only for control**: control keywords (`pause`/`resume`) and reauth code replies still come through the primary DM chat, which is where `isTrustedController` anchors. The one inbound authority it carries is the settings tier above (`isMaintainerController`) — deliberate and narrow: it may change what the hermit *is configured to do*, never who may reach it (the enrollment root stays terminal-only), and it cannot pause, resume or interrogate the session. Adding a `maintainer_channel_id` therefore widens what the hermit *tells* a second chat, plus exactly one thing that chat may *settle*. The model composes both audience versions and delivers them through `channel-send.ts --notice` (a direct platform POST with the bot token, config-pinned target); deterministic callers use the equivalent `--tier maintainer` mode. Neither path touches the channel plugin's `access.json` — the maintainer chat needs the bot present in it, not an access grant.

## Script Argument Trust

The sealed allow-list grants whole scripts, not individual invocations: `Bash(bun */scripts/proposal.ts*)` pre-approves **every argument** that call can carry. Outside auto mode those wildcards resolve normally — probed live on CC 2.1.220, a command matching a mid-string `*` rule runs with no prompt — so a script reached this way must treat its own argv as untrusted input. Two argument classes were reachable before this was enforced:

- **The state dir.** Every production call passes the literal `.claude-code-hermit` from the project root, but the argument was taken as given, so a single pre-approved call could resolve, dismiss, or patch *another project's* proposals. `proposal.ts` now pins it: the argument must resolve to `hermitDir()` for the current project, and a mismatch is a usage error (stderr, exit 1) rather than a stdout verdict, because several verbs own distinct stdout grammars their callers branch on. The shared check is `assertStateDir()` in `scripts/lib/cc-compat.ts`. It accepts two roots, not one: `hermitDir()`, and the main checkout's state dir resolved via `git rev-parse --git-common-dir`. The second is required because hermit state is deliberately main-rooted and shared across worktrees, so a worktree session legitimately passes main's absolute path — and for an out-of-tree worktree (`git worktree add ../wt`) the walk-up cannot reach main and fails open to the projection. Pinning to `hermitDir()` alone breaks every proposal write from a worktree — the exact case `proposal.ts` exists to serve, since Write/Edit are blocked there. The git lookup runs only after a mismatch (so the common path spawns nothing) and resolves from our own cwd, so it can never name a foreign project. On the argv side, `assertStateDir()` first normalizes a worktree *projection* (the `.worktreeinclude` copy: config.json present, no `state/`) to the root its own walk-up finds, so the relative `.claude-code-hermit` the CLAUDE-APPEND commands pass resolves to main from inside a worktree instead of being refused. That is not a widening — the normalized root still has to equal one of the two accepted roots, so a foreign projection normalizes to its own foreign root and is rejected exactly as before. `manifest-seed.ts`, `reflect-precheck.ts`, `archive-shell.ts`, `session-archive.ts`, `channel-log.ts`, `observations.ts`, `evolve-finalize.ts`, `transcript-digest.ts` and `channel-send.ts` all adopt the same `assertStateDir()` pin. Two carry a narrower shape: `archive-shell.ts` pins only its `--state-dir` argv (its `HERMIT_STATE_DIR` fallback needs an env prefix, so it is already outside the grant); `transcript-digest.ts` pins only an *absolute* argv, because a relative one is deliberately ignored in favor of the `hermitDir()` walk-up and pinning it would turn that cwd-drift fallback into a refusal. A third, `channel-send.ts`, pins the full argv but exits **2** on a mismatch rather than the shared helper's 1, because it documents 1 as "a leg failed to land" and 2 as "the caller got it wrong, nothing was sent" — a foreign state dir is the latter, and reporting it as the former would read as a broken channel. `channel-send.ts` is the sharpest instance of this class: it is an egress path, so an unvalidated root meant sending with *another* project's bot token to *that* project's configured chat. `evolve-plan.ts` is the one directly-granted script left unpinned, and deliberately: it writes nothing. `reflect-precheck.ts` forwards its argv to `archive-shell.ts`, `archive-raw.ts` and `update-reflection-state.ts` as a subprocess argument, so its pin covers those hops — but **a forwarding pin is not a substitute for a script's own.** `archive-shell.ts` also carries its own `Bash(bun */scripts/archive-shell.ts*)` grant, so it is reachable without passing through `reflect-precheck.ts` at all, and needs (and now has) its own check; only `archive-raw.ts`, which has no direct grant, is genuinely covered by the forwarding alone. **When auditing this class, enumerate the sealed allow-list in `apply-settings.ts`, not the call graph** — a direct grant means a direct entry point.
- **A file (or subdirectory) inside the state dir, not the state dir itself.** `update-reflection-state.ts`'s argument is the reflection-state *file*, and `generate-summary.ts`'s CLI-mode argument is the `<hermit>/state` subdirectory — an exact-equality check against `hermitDir()` would reject every legitimate call. `assertUnderStateDir()`, alongside `assertStateDir()` in `cc-compat.ts`, checks containment (resolves under one of the same two accepted roots) instead of equality. `update-reflection-state.ts` was the worst-shaped instance of this defect class before the fix: its argument was a **file path**, not bounded to a directory at all, so an unvalidated call could write arbitrary JSON at arbitrary depth on disk. `generate-summary.ts`'s **hook mode stays unpinned deliberately** — it derives its path from a PostToolUse payload for a write that already happened, and a hook is not reachable through the `Bash(...)` grant the CLI path is.
- **Path fragments joined onto a state-dir subpath.** `proposal.ts patch` joined its filename onto the proposals dir unvalidated, so a `../` prefix reached any frontmatter-bearing `.md` on disk at arbitrary depth. It now requires a direct-child basename. Absolute paths were never an escape here — `path.join` re-roots them — and a regression test pins that.
- **Test-seam flags that accept caller-supplied state.** `domain-hatch.ts` carried `--state-dir`, `--project-root` and `--plugin-list-file` purely so its tests could avoid shelling out to a live `claude`. All three were reachable in production through the `Bash(.claude-code-hermit/bin/hermit-run domain-hatch <verb> *)` grants. The first two are the same state-dir defect as above; `--plugin-list-file` is worse — a forged plugin list steers `resolvePlugin()` → `installPath` → `planBlock()`, which reads a CLAUDE-APPEND block from that path and writes it into the operator's `CLAUDE.md`, so a forged list is attacker-authored content landing in the file that steers the agent. Rather than validate these, all three were **removed**: `stateDir`/`projectRoot` are now always derived from `hermitDir()`, and the plugin list is always live. Argv beyond `<plugin-id>` is now allow-listed per verb, exiting 1 with `unexpected_args` on anything else. Tests exercise the removed seams' old coverage at the library boundary (`lib/domain-hatch/preflight.ts`, `target.ts`) with explicit roots, rather than through CLI overrides.

`proposal.ts quality-gate` (reached as a verb, not a standalone script) was checked during this pass and needs no change: it falls through to `proposal.ts`'s own `requirePinnedStateDir()` before ever reaching `lib/proposals/quality-gate.ts`.

**The sanctioned override is an env prefix, and that is what makes it a boundary.** `hermitDir()` honors an absolute `AGENT_DIR` ahead of the cwd walk-up, which is how tests target a scratch state dir. Probed on CC 2.1.220: `AGENT_DIR=/tmp/x bun <dir>/scripts/literal.ts go` requires approval even though the identical command without the prefix is covered by an allow rule — an env assignment moves the command outside the rule's prefix match. So redirecting a hermit script at a foreign root cannot be done silently under the sealed grant.

Applies to any script reached through a wildcarded interpreter grant, not just `proposal.ts`. When adding one, assume its arguments are attacker-chosen and validate the state dir (or, if the argument is a file/subdir under it, use `assertUnderStateDir()`) and any joined path fragment. Prefer removing a caller-supplied override entirely (as `domain-hatch.ts` now does) over validating it, when nothing production-side actually needs the override.

## Bash Sandbox

Hermit does not probe for or configure Claude Code's native bash sandbox (`sandbox.*` settings, `bwrap`/`sandbox-exec`). Predicting whether CC's own sandbox spawn would succeed from outside CC proved unreliable — a false-positive probe could enable a sandbox profile that then broke every subsequent Bash call, with no in-session recovery. `/hatch` instead prints a one-time pointer to CC's own setup: run `/sandbox` (its Dependencies tab checks `bwrap`/`socat` for you) or see the [sandbox docs](https://code.claude.com/docs/en/sandboxing).

**Docker:** `bubblewrap`/`socat` stay installed in the hermit image so `/sandbox` is available in-container if you want it, but hermit writes nothing (Claude Code's sandbox is off by default). The container boundary (`cap_drop:ALL`, `no-new-privileges`, network policy) is the isolation layer Anthropic recommends for unattended runs, and the nested bwrap sandbox is optional defense-in-depth on top of it (https://code.claude.com/docs/en/sandbox-environments). Note: on Ubuntu 24.04+ hosts (`kernel.apparmor_restrict_unprivileged_userns=1`, the 23.10+ default) the AppArmor `docker-default` policy blocks `bwrap` from creating user-namespaces in-container, so an in-container sandbox may not start there and — if forced on regardless — would silently kill heartbeat and `/watch` Monitor subprocesses.

**Enabling or disabling:** entirely the operator's call — run `/sandbox` or edit `sandbox.enabled` in your settings file directly. Hermit never writes this key.

**Credential protection:** Claude Code's default sandbox read policy still allows reads of `~/.aws`, `~/.ssh`, and `~/.gnupg`. If you enable the sandbox, add a `sandbox.credentials` block (or `sandbox.filesystem.denyRead`) to block them — earlier hermit versions wrote these denies for you, but hermit no longer manages `sandbox.*`, so this is now yours to set. See the [sandbox docs](https://code.claude.com/docs/en/sandboxing#protect-credentials).

**Custom CA / MITM proxies:** tools that use a corporate proxy with a custom certificate authority may need `"enableWeakerNetworkIsolation": true` in the `sandbox` block. See the [FAQ](faq.md) for details.

## Login Token Handling

Docker hermits on subscription auth hold a long-lived `setup-token`. Renewal relays through the operator's chat channel, so it's worth being precise about what crosses that channel and what doesn't.

**Crosses the channel:** the one-time OAuth sign-in URL, and the short-lived login code the operator pastes back. Both are single-use and worthless once the flow completes. On an install with a `maintainer_channel_id` configured, the URL is routed to the maintainer chat (via `channel-send.ts --tier maintainer`, marked sensitive so it is not written to the searchable channel log) rather than the primary client chat; the operator still pastes the code back through the primary DM chat, which remains the only inbound surface.

**Never crosses the channel:** the token. It is captured from the mint process's own terminal pane and written directly to a `0600` file on the container's config volume. It is never printed to stdout, never logged, never included in a channel message, and never returned by any script that a skill or the model can read — the install path returns only `{ok, expires_at}`. The renewal skill relays a link it was handed; it never sees the credential.

**Where the token lives, and where it doesn't:**

| Location | Holds the token? | Why |
| --- | --- | --- |
| `<config-dir>/.hermit-setup-token` | Yes, `0600` | Persistent volume, survives restarts, rotatable in place |
| `state/setup-token.json` | No — only `{minted_at, expires_at}` | Doctor and the watchdog need expiry, not the secret |
| `.env` / docker-compose | **No, deliberately** | `env_file` applies at container creation, so a token there could not be rotated without a host-side recreate |
| tmux env-file (`/tmp/.hermit-env-*`) | Transiently, `0600` | Sourced then deleted by the shell that launches claude |
| Mint pane scrollback + capture file | Transiently, `0600` | Both destroyed on every exit path, including aborts |

The reactive recovery path runs entirely in the watchdog with no model involvement — a hermit with a lapsed login cannot reason, so the flow that recovers it must not depend on reasoning. It also waits for an explicit operator acknowledgement before minting anything, so an attacker who can observe the channel still cannot cause a link to be issued on demand.

## Container Hardening

`/claude-code-hermit:docker-setup` (v1.0.26+) renders three kernel-enforced hardening stanzas into `docker-compose.hermit.yml`. These are defense in depth — they reduce the blast radius of a successful prompt injection or a compromised plugin. They are **not** a substitute for the upstream defenses (deny patterns, non-root user, named-volume isolation, no host secret mounts) and they don't make the container "safe against prompt injection." They make a successful injection less useful.

Honest weighting:

| Stanza                                   | What it does                                                                   | Real teeth?                                                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `security_opt: [no-new-privileges:true]` | Blocks setuid escalation at the kernel level, even via planted setuid binaries | **Yes** — closes a real vector against future supply-chain compromise of any installed plugin              |
| `cap_drop: ALL`                          | Revokes Linux capabilities (NET_RAW, SETUID, DAC_OVERRIDE, …)                  | Incremental — non-root `claude` user already had no ambient caps; this closes the kernel-enforced ceiling  |
| `pids_limit: 2048`                       | Caps process count (fork-bomb / runaway-subprocess bound)                      | Resource bound, not a security primitive on its own — limits collateral damage                             |

Hermit's runtime (tmux, claude CLI, bun, jq, npm, git+HTTPS plugin installs) needs none of what these stanzas remove. Steady-state PID usage is ~80; install bursts can spike higher but stay well below 2048.

**Override path.** Operators with custom workloads (services on ports <1024, setuid helpers, high-PID frameworks) edit `docker-compose.hermit.yml` directly to relax or remove the relevant stanza. The defaults are conservative because the recommended-plugins flow accepts third-party marketplaces — every operator who didn't audit every plugin benefits from the floor.

**Verifying it's active.** From the host:

```bash
# Capabilities — both should be 0000000000000000
docker compose -f docker-compose.hermit.yml exec hermit \
  grep -E '^Cap(Eff|Bnd)' /proc/self/status

# no-new-privileges — should report NoNewPrivs: 1
docker compose -f docker-compose.hermit.yml exec hermit \
  grep NoNewPrivs /proc/self/status

# PID limit — should report 2048
docker compose -f docker-compose.hermit.yml exec hermit cat /sys/fs/cgroup/pids.max
```

**Limitation.** These flags only apply at container creation, not on `restart`. After patching an existing compose file, run `hermit-docker down` then `hermit-docker up` — `hermit-docker restart` silently keeps the old container.

### Advanced hardening — `/docker-security`

Beyond the always-on baseline above, `/claude-code-hermit:docker-security` is an opt-in advanced wizard that adds a `docker-compose.security.yml` overlay with LAN containment + DNS policy (firewall + DNS sidecar with port-53 redirect for actual enforcement), resource bounds + kernel hygiene sysctls, and a boot-time plugin-install audit log. Each toggle is presented with honest cost/benefit framing, applied as an overlay (does not modify `docker-compose.hermit.yml`), verified against the live container, and fully reversible. The LAN containment toggle is hard-skipped when `docker.network_mode: "host"` is in use. Honest limitation surfaced in the wizard and dedicated docs: DNS policy blocks domain-based exfil but cannot stop direct-IP egress to a hardcoded public address. See [Docker Security](docker-security.md) for the full toggle reference, verify commands, and documented limitations.

### Known limitations

- **`hermit-doctor`'s `channel-liveness` check and the deterministic channel-send path (`lib/channel-send.ts`) are two of core's direct outward egress paths.** Doctor's liveness call (Telegram `getMe`, Discord `/users/@me`) sends no message content, 5s timeout, fail-soft. `channel-send.ts` does send message content — it is the mechanism behind the watchdog's lifecycle pushes (restart/wedge/forced-pause), `cost-tracker`'s budget-cap alerts, and the `lib/prompt-stages/channel-status-responder.ts` reply — reading the bot token straight from the already-configured channel's `state_dir/.env` (the same token the channel MCP plugin uses), a plain-text POST with an explicit 10s timeout, and no retry on failure (fail-open: the caller falls back to its existing model-mediated path). Every other doctor check is a local filesystem read. The docker-security DNS allowlist already covers both platform hosts (`telegram.org`, `discord.com`) — no allowlist change needed. Disabling a channel disables both its liveness probe and any push through it; there is no separate per-check opt-out in v1.
- **Remote control and status disclosure trust the operator DM when no `allowed_users` is set.** A plain channel *reply* still follows the documented accept-all default when `channels.<channel>.allowed_users` is absent — but the two paths that either *mutate state* (`pause`/`resume`/`snooze` via `lib/prompt-stages/pause-keyword.ts`) or *disclose operator state* (the deterministic `status` reply) do **not**. With no allowlist configured they trust only the operator's pinned home chat (`chat_id === channels.<channel>.default_chat_id`, falling back to `dm_channel_id` until the pin is seeded); any other sender's control keyword is a silent no-op, and any other accepted sender gets a redacted, coarse status (no spend figures, task text, or pending-approval IDs). The anchor is the *pinned* home rather than the last-learned DM because `dm_channel_id` follows whichever chat wrote last: anchoring there meant control authority could be **acquired** by messaging from a new chat. `default_chat_id` is seeded once and moves only from the terminal, so that path is closed. `<channel>` here is the normalized bare server name (`lib/channel-envelope.ts`'s `normalizeChannelSource`) — the harness injects a plugin-qualified `source` on the wire (`plugin:discord:discord`), but config keys channels by the bare name, so this gate resolves the qualified source back to it before every lookup. **Caveat (unchanged by the pin):** if a channel's home *is* a group/server channel, `default_chat_id` equals that shared chat, so every member of it matches the binding — those installs must set `allowed_users` explicitly to restrict control and full status to named operators. Pinning closes the *acquisition* path (a new chat can no longer become the anchor by messaging); it does not narrow a home that is itself shared, because the match is per-chat, not per-sender. This is a flat trust list, not RBAC (an RBAC pass on `allowed_users` is a deliberately-deferred enterprise gap).
- **Telemetry export is another direct outward egress — opt-in, off by default.** `config.telemetry_export` (absent or `enabled: false` = nothing ever leaves the box) periodically POSTs a versioned health/cost bundle to an operator-configured webhook from the watchdog tick. The bundle is allowlist-built: only named numerics/enums/counts are copied in by default (cost totals, doctor check statuses, alert counts, session cost/duration, watchdog event counts); free text (task descriptions, error messages, alert detail strings) is included only when the operator explicitly sets `redact_operator_text: false`. The bearer token comes from an env var named in config, never from `config.json` itself, and neither the webhook URL nor the token ever appear in logs or error output. Under docker-security, the webhook's host must be added to the DNS allowlist or exports fail (and spool) inside the hardened container.
- **Three artifact pages publish session-derived content to claude.ai — default on, per-page opt-out.** `config.artifacts.dashboard`/`proposals`/`weekly_review` (default `true`) each publish a rendered page — status/latest-brief/proposals/weekly-evolution, open-proposal full text, and the compiled weekly review, respectively — via Claude Code's built-in Artifacts feature, not a hermit-authored HTTP call. **This paragraph describes `config.artifacts.backend: "claude"`, the default; the sentences about the built-in feature, its governing controls, and Anthropic-side privacy do not carry over to any other backend (next bullet).** On the default backend it's the same publish path as any other Artifact a session creates, so it's governed by Claude Code's own controls (`disableArtifact`, `CLAUDE_CODE_DISABLE_ARTIFACT`, `permissions.deny`), not the docker-security DNS allowlist. Private to the publishing account on Pro/Max; Team/Enterprise can additionally Share within the org, never across it. Every automatic publish is a deterministic render of enumerated state files — with one caveat: the dashboard's latest-brief section embeds `state/last-brief.json`, whose `text` field is itself model-composed by the `brief` skill, so that one section is not exclusively machine-generated content. On-demand publish of a compiled doc or proposal (operator-initiated, no config gate) is likewise a direct file publish, no model authorship. A hermit that ran `/hermit-dashboard-design` is the second caveat — see the next bullet. See `docs/config-reference.md#artifacts` and `docs/artifacts.md`.
- **A custom dashboard renderer is operator-owned code core executes on the automatic path.** `/hermit-dashboard-design` writes `.claude-code-hermit/dashboard-render.ts`, and the file's *presence* — no config flag — makes `artifact.ts render dashboard` `spawnSync` it and publish whatever it produced. Two properties change for that hermit. First, the dashboard is no longer a deterministic render of enumerated state files: its layout, its data selection, and its escaping are model-authored once and then replayed unattended on every brief, so the "no free-form model-authored pages on the automatic path" assurance below holds only for a hermit with no renderer installed. Core validates the receipt, never the page — no structural check, no escaping pass — by design (`docs/artifacts.md` § Custom renderer); the escaping discipline lives in the skill that writes the file. Second, a routine dashboard refresh becomes a code-execution point: whoever can write that path gets code running under the hermit's own identity at every refresh, behind a command line that reads as a core render call. It is a *persistence* surface, not a new privilege — writing it takes the same file-write capability an attacker would already need — but it is durable across restarts and invisible to a reviewer watching Bash commands, so treat an unexplained `dashboard-render.ts` the way you would an unexplained hook. Unlike the sealed-allow-list scripts below, `artifact.ts` takes its state dir as given (it holds no direct `permissions.allow` grant, so every call is classified on its own), which means the executed path follows that argument — audit the argument, not just the verb.
- **A non-`claude` artifact backend sends the same content to a host the operator chose, under the operator's own grant.** Setting `config.artifacts.backend` to a connected MCP artifact server routes every page publish there instead of claude.ai. Registering that server, minting its token and granting its tool permissions are done by the operator by hand — that manual setup, not the config key, is the consent act, and the plugin adds no permission for it — `hermit-start`'s boot grant covers only the native `Artifact` tool, and is skipped on a non-`claude` backend so an install that forbids publishing to claude.ai does not newly acquire a standing prompt-free grant for exactly that. Skipping is not revocation: a hermit switched over after boots on the default backend keeps the `Artifact` entry already in `permissions.allow`, and removing it is a manual edit. Consequences to weigh: the content is the same session-derived render, but the Anthropic-side privacy and governance properties in the bullet above no longer apply — retention, access control and sharing are whatever that server implements, and its egress is subject to the docker-security DNS allowlist like any other outbound host. Failure is strict-skip, never a silent fallback to claude.ai, so a misconfigured backend cannot leak a page to the other host. Core hardcodes nothing about any particular server; the publish protocol comes from the server's own MCP `instructions`, which also means the trust placed in those instructions is the operator's to assess.
- **`permissions.allow: ["Artifact"]` is a sanctioned pre-approval of an outward-publishing tool for autonomous use.** Applied via the `artifacts.publish_authorized` config flag (§ Auto-mode Classifier above) so unattended sessions don't stall on the first-publish permission ask (a headless "ask" is an effective deny) — a channel reply sets the flag only, and `hermit-start`'s boot-time grant, running outside any session, is what actually writes the permission (needed because the classifier blocks a session from widening its own `permissions.allow`, even attended-seeded). Re-ensured every boot, so a hand-wiped entry heals itself; revoke via `/hermit-settings artifact-authorization`. Assessment: a published artifact is private to the publishing account until someone shares it from the page's share menu, so a prompt-injected publish is persistence/noise rather than exfiltration — reaching an attacker still requires a human to share the page, and `channel-send.ts` (above) remains the materially riskier egress. The real cost is losing the human checkpoint before irreversible external persistence: there is no tool-side delete, and published content may be cached even after removal from the gallery, so a mistaken publish (e.g. a render that embeds a secret that leaked into state) can't be fully recalled. Mitigation: every automatic-path publish is a deterministic render of enumerated state files (no free-form model-authored pages on the automatic path — see the brief-text and custom-renderer caveats above); operators who decline the flag get the same outcome via setup-time banking (first publish happens inline, attended, at hatch/evolve time) instead of a standing grant.
- **Egress filtering is opt-in.** Bridge networking isolates from localhost but the container can still reach the internet by default. A successful prompt injection can exfiltrate data to external hosts. **Mitigation available**: `/claude-code-hermit:docker-security` adds LAN containment + DNS policy via a firewall sidecar with kernel-level port-53 redirect for real enforcement. **Remaining gap**: direct public-IP egress (hardcoded IPs, no DNS) is not blocked even with the wizard — v1.1 may add nftset-driven IP allowlisting. See [Docker Security](docker-security.md).
- **No input sanitization for fetched content.** Content fetched from external APIs enters Claude's context unsanitized. Deny patterns cannot catch injection via fetched content — that's an instruction-following boundary, not a mechanical one. **The scheduled-wake surface is now scanned.** HEARTBEAT.md is model-editable and feeds the autonomous evaluation subagent verbatim, so a poisoned checklist item written in one session could steer every future wake. `heartbeat.ts precheck` scans it pre-wake for three pattern classes (instruction-override phrases, context-marker tags, decode-pipes); a hit converts the tick into an operator alert and suspends checklist evaluation until the file is edited. The suspension is scoped to checklist evaluation only — deterministic operator-safety notifications still fire (a pending budget alert pierces the announced-damper; a due stale auto-close still runs), since neither reads HEARTBEAT.md. This breaks the self-persistence path but is defense-in-depth, not a boundary — the PreToolUse/permissions chokepoint remains the actual guard during any wake turn.
- **Deny patterns are a blocklist.** They catch commands you anticipated. Equivalent commands not on the list execute normally. Bind mount scope and network isolation are stronger defenses for novel attacks. The runtime hook (`enforce-deny-patterns.ts`) additionally normalizes each Bash candidate (whole command and every compound segment) before matching — collapsing horizontal whitespace runs, backslash-newline continuations, and unquoted `$IFS`/`${IFS}` — so a pattern like `rm -rf` also catches `rm  -rf`, `rm${IFS}-rf`, and the same hidden behind `&&`/`;`/`|`. Deliberately **not** implemented: Unicode normalization (NFKC), ANSI/NUL stripping, base64/decode-pipe detection, or general flag-order canonicalization. Bash does not treat those as equivalent to the canonical spelling — e.g. a fullwidth `ｓudo` is a distinct token that fails with "command not found," not an executable bypass — so folding them would close a non-threat while adding false-positive surface on legitimate unicode/binary arguments. This mirrors a full deobfuscation pipeline (as competitor agents implement as their *only* execution boundary) being disproportionate here: it sits behind the bash sandbox and container hardening layers above, not in front of an unsandboxed process.
- **Episodic channel-log (PROP-010) stores raw DM text locally.** `state/channel-log.sqlite` holds the operator's Discord/Telegram DM text verbatim — capture is gated by the same `channels.<channel>.allowed_users` allowlist channel-responder enforces (envelope source normalized to the bare channel key, same as above; unauthorized senders are never logged), but authorized senders' full message text is retained until weekly-review consolidation and its retention window prune it. Storage is deliberately unsanitized (fidelity for consolidation), but the `/recall` read path (`search.ts`) runs recalled text through `safeForLLM` — the same control-char/tag-impersonation defusal `lib/prompt-stages/channel-reply-reminder.ts` already applies to the envelope's `source`/`chat_id` — before it reaches model context. Treat it as untrusted external input regardless: it's the operator's own words, but unreviewed. The file is local-only, covered by the standard `state/` gitignore, and never committed. Disable capture with `knowledge.channel_log_enabled: false` if this tradeoff isn't wanted.

## Plugin Security

### Trust Model

Installing a plugin runs that plugin's hooks and skills with the same authority as hermit. Only install plugins from sources you trust the same as hermit itself. The container hardening in `docker-compose.hermit.yml` (`cap_drop`, `no-new-privileges`, `pids_limit`) reduces what a *compromised* plugin can do to the host kernel — it does not vet the plugin's intent, sandbox its file access within the project, or prevent it from acting on your behalf via the agent. A malicious or careless plugin still runs as you.

Plugins run with the same permissions as Hermit. The default `auto` mode applies classifier review to each action; if the operator has opted into `bypassPermissions` for fully unattended Docker operation, plugins run with full unrestricted execution — no permission prompts, no human review.

**Policy:** The entrypoint installs every enabled entry in `docker.recommended_plugins` on first boot, regardless of marketplace. The trust gate is at **configuration time**: entries only land in `config.json` when the operator explicitly confirmed the mirrored plugin list during `/docker-setup` or `/hermit-settings docker`. Preselection during setup is restricted to `claude-plugins-official` and `gtapps/*` — third-party entries must be manually opted in. See [Recommended Plugins — Trust model](recommended-plugins.md#trust-model).

**No auto-updates:** The entrypoint installs plugins on first boot but never auto-updates them. Plugin updates are operator-initiated via `/claude-code-hermit:hermit-evolve` or image rebuild.

**Hermit does not vet, audit, or take responsibility for any plugin.** Even official plugins should be understood before enabling. You are responsible for evaluating what you install.

See [Recommended Plugins](recommended-plugins.md) for the full list and installation instructions.
